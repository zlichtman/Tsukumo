A Cloudflare Worker with one SQLite-backed Durable Object per device and a `Registry` object: the Mac keeps one outbound WebSocket, registers a P-256 public key and gets an unguessable device id, and proves its key on every connect by signing a stateless, single-use nonce from `/challenge` in the upgrade request (no socket exists until the key is proven); each device is `https://<id>.<domain>` on a wildcard domain (recommended) or `https://<host>/d/<id>` on workers.dev. Public requests (and the path-inserted `.well-known` forms) are forwarded over the socket as JSON frames, bodies streamed both ways under a 1 MiB flow-control window and a 48 MiB memory budget per isolate that every held byte is charged to until it's gone, with cancel, upload deadlines (408), a 60-second answer timeout (504), 503 when the Mac is offline, a 12 MB body limit, rate limits per IP and per device, 8 requests in flight per device, every page sandboxed to an opaque origin with cookies and service workers refused, 30-day leases, a 10,000-device cap, and 3 registrations a day per address. It logs no content, and Cloudflare's invocation logs and traces are off. ## Build

All three are built with Xcode 26 or later. The apps are XcodeGen projects: run `xcodegen generate` in `apps/macos/` or `apps/ios/` after pulling; the generated `.xcodeproj` is never committed. Build one project at a time; several builds at once saturate the Mac.

**There's no test suite** (October 8, 2026; the owner: "we're going to just ship stuff and I will find the errors"). Write the safest code you can, and when testing one thing by hand (or with a throwaway check that isn't kept) is what would catch an error, do that. **`scripts/build.sh`** builds what a change touched, against `origin/main` (or `main` on a branch), committed or not: the Mac app when `apps/macos` or TsukumoKit changed, the iPhone app for the simulator when `apps/ios` or TsukumoKit changed, the relay's typecheck, and `zsh -n` on changed scripts (`--all` builds everything). Builds go to one incremental cache per checkout in `~/Library/Caches/Tsukumo`. A review (Codex, `--ephemeral`, read-only) is for a risky change to data, security, or sync, once, not a loop.

**TsukumoKit:** `swift build` (no xcodebuild). The apps also add `TsukumoKit/MLXVoice` (Whisper and Kokoro on MLX, with the part of mlx-audio-swift they need vendored; `swift build --package-path TsukumoKit/MLXVoice --scratch-path /tmp/tsukumo-mlxvoice-build` builds it alone). Pass `--scratch-path` outside iCloud Drive to keep build products out of it.

**The Mac app (`apps/macos`):** `xcodegen generate` in `apps/macos/`, then build and open it:

## Release

- **iPhone** (`apps/ios`, `com.zlichtman.tsukumo`; the version stays 1.0.0 and the build goes up, AGENTS.md rule 2):
  1. Build: `scripts/build.sh` (Build, above).
  2. Run `scripts/upload-testflight.sh <N>` from the main checkout. It sets `CURRENT_PROJECT_VERSION` in `apps/ios/project.yml` to N, runs `xcodegen generate`, archives the `Tsukumo` scheme (Release, `generic/platform=iOS`), checks the archive's build and bundle ID, and uploads it with `apps/ios/ExportOptions.plist` (app-store-connect, destination upload), signing in with the App Store Connect API key in `~/.appstoreconnect` (never a password). `--no-upload` stops after the archive; `--out <folder>` keeps the archive and logs there. It waits for any other xcodebuild first.
  3. Commit the bump, report Apple's real processing and TestFlight status, expire the previous build, and add `docs/releases/TSUKUMO-IOS-<N>.md`.
- **Mac** (`apps/macos`, `com.zlichtman.tsukumo.mac`; one notarized Developer ID build for everyone, installed with Homebrew, `brew install --cask zlichtman/tap/tsukumo`, or from the owner's website; only when the owner approves a release). The version is 2.<NN> (AGENTS.md rule 2): build 200 is version 2.00.
  1. From `main` in the main checkout, with the screen unlocked, run `scripts/release-mac.sh <N> [--notes "<one line>"]`. When the script itself changed since the last release, try it first with `--dry-run --out <folder>`: that tests, builds, notarizes, and checks a real candidate, then prints the site, feed, cask, and bump changes without committing, pushing, deploying, or tagging. Otherwise skip the dry run: the real run does the same checks before it publishes anything, and a dry run first doubles the tests, the build, and two notarizations.
  2. The script waits for other xcodebuild or notarytool runs and for an unlocked screen, exports `git archive HEAD` with the build number set, and builds the app from it:
     - **Default (no Developer ID profile installed):** archived with `TSUKUMO_CAPABILITIES=Local`, manual Developer ID signing, and no provisioning profile; the script checks that no iCloud or Sign in with Apple entitlement slipped in and that `TsukumoCapabilities` is `Local`.
     - **With iCloud and Sign in with Apple:** used automatically once a Developer ID profile for `com.zlichtman.tsukumo.mac` carrying the container `iCloud.com.zlichtman.tsukumo` and Sign in with Apple is installed (made in the developer portal with the Developer ID Application certificate), or forced with `--with-icloud`. It archives with `TSUKUMO_CAPABILITIES=iCloud` and automatic signing and exports `developer-id` with that profile, then checks the container, Production CloudKit, Sign in with Apple, and the embedded profile.
     - Either way: hardened runtime, no `get-task-allow`, the app notarized and stapled, then the themed DMG (`scripts/dmg`, dmgbuild in `~/.venvs/dmgbuild`) signed, notarized, and stapled.
  3. Website (the Portfolio site, deployed only with the Vercel CLI from a clean `git archive HEAD` export): `public/downloads/Tsukumo-2.<NN>.dmg` replaces the previous DMG in the same commit (Homebrew's audit refuses a fixed sha256 on an unversioned URL), `next.config.ts`'s `tsukumoDownload` makes `/downloads/Tsukumo.dmg` a temporary redirect to it, and `public/downloads/tsukumo.json` is what the app's Software Update reads (and the cask's livecheck reads its `version`). Only those paths are committed, as the no-reply identity. The live DMG must answer 200 with the same SHA-256. The feed is exactly these six keys, as `json.dumps(…, indent=2)` writes them, and the script refuses anything else (the app refuses it too):

     ```json
     {
       "version": "2.04",
       "build": 204,
       "url": "https://zlichtman.com/downloads/Tsukumo-2.04.dmg",
       "sha256": "<the DMG's SHA-256, 64 lowercase hex digits>",
       "minimumMacOS": "26.0",
       "notes": "<the --notes line: one plain line, at most 300 characters, no em dash, never \"Kemo\">"
     }
     ```

     `version` is 2.<NN> and `build` its integer (`CFBundleVersion`; the app compares builds); `url` must be HTTPS on exactly `zlichtman.com` under `/downloads/` and end in `.dmg` (the app follows redirects only within that host, so `/downloads/Tsukumo.dmg` can't be the feed's URL if it ever redirects elsewhere); `minimumMacOS` is `apps/macos/project.yml`'s deployment target; `notes` show under "Version 2.04 is available" in Settings, General, and in the "ready to install" notification. **Whoever publishes a Mac build by hand (as 2.00 to 2.03 were) publishes this file with the DMG, in the same deploy**, or no copy of the app sees the update; a feed whose `sha256` doesn't match the live DMG makes every copy refuse it.
  4. Homebrew: `Casks/tsukumo.rb` in `zlichtman/homebrew-tap` gets `version "2.<NN>"`, the sha256, the url `Tsukumo-#{version}.dmg`, a livecheck returning the feed's `version`, `uninstall quit: "com.zlichtman.tsukumo.mac"`, and `auto_updates true` (the app updates itself from `tsukumo.json`, so plain `brew upgrade` leaves it to the app and `brew upgrade --greedy` still updates it; the old 1.80 cask had the same line); everything else stays (`depends_on macos: :tahoe`). `brew style` and `brew audit --cask --online` must pass before it's pushed, as the no-reply identity. Leave the tap's other casks alone.
  5. It checks the live DMG, the redirect, the feed, and `brew update` + `brew fetch --cask`, then commits and pushes the build number bump to `main` (or only pushes, when the bump is already committed). No git tag. Record the build in the status table above and in `docs/releases/`.
  6. Never a GitHub release; the tap holds casks only.

## Known issues

1. **The iPhone app hasn't run on a real iPhone or reached TestFlight.** It's tested on simulators only, so KemoSabe's own replies on a real iPhone and on-device extraction from real data are unchecked; no real API turn ran (no key in tests). Apple's on-device model answers on an iOS 27 simulator; an iOS 26.2 simulator on a macOS 27 Mac fails generation with error -1. Not built yet: a consent request as a notification.
2. **Tsukumo's Dock hasn't been seen on screen with live glass.** Its windows were saved from inside the app (`--capture`), which can't draw Liquid Glass, the shelf's vibrant tiles, or the bubble's glass text. Not checked: a real Sign in with Apple, a real API key, Calendar access prompts, the login item on a copy in /Applications, and a real preview build's data and Keychain items. 2.00 went to the website by hand after `scripts/release-mac.sh 200 --dry-run`, since the script's publish step also updates Homebrew; the full script hasn't run for this app. When the cask moves to it, the old app's 1.80 updater will read 2.00 in `tsukumo.json` and refuse it (another bundle ID), so owners of the old app move with `brew upgrade --cask tsukumo` or a download; its data in `~/Library/Application Support/KemoSabe` isn't brought over. Not ported from the old dock: the review panel and chirps as lines in Together.
3. **iCloud sync and Sign in with Apple wait on the owner's approval in Apple's developer portal.** Built and tested against the in-memory database (`LibrarySyncTests`) and with the Sign in with Apple stand-in; no build carries the entitlements (`TSUKUMO_CAPABILITIES = Local`), so no real CloudKit call or Apple sign-in has run. To turn them on, the owner approves, for App IDs `com.zlichtman.tsukumo` (iPhone) and `com.zlichtman.tsukumo.mac` (the Mac app): the iCloud capability with CloudKit and the container `iCloud.com.zlichtman.tsukumo` (created once, shared by both), and Sign in with Apple (the iPhone as primary App ID, the Mac app grouped with it); then build with `TSUKUMO_CAPABILITIES=iCloud` and check two real devices. Website and Homebrew builds also need a Developer ID provisioning profile carrying both (`release-mac.sh` uses it once it's installed). Not built yet: CloudKit push subscriptions (sync runs on launch, on returning to the app, and after local changes).
4. **Coding agents haven't finished a real turn in the app.** The backends are tested against fake CLIs speaking each protocol, and one real read-only turn each ran through them on this Mac (Last verified, above): Codex finished; Claude Code and Cursor Agent stopped at their own sign-ins (expired, and "Authentication required"), so a full Claude Code or Cursor turn, an approval from a real agent, a real `ask_kemosabe` call, and a resumed session haven't been seen live yet (resume uses the old app's flags: `--resume`, `thread/resume`, `session/resume` or `session/load`). Not built: Tsukumo's tools over ACP (that needs a stdio MCP server the agent starts, or the KemoSabe gateway over HTTP, not wired yet), ACP terminals (agents run commands with their own tools and ask first), Muse Code (the old app's adapter was checked against its schema, not a live turn, so it wasn't ported; a Muse bot says it isn't supported), worktrees per task, the review panel, and adding your own ACP agent in Settings. Codex in Read only may run commands inside its own read-only sandbox without asking (it can't change files); Codex's commentary before its answer is part of the reply. Gemini CLI's `--experimental-acp` flag is from its documentation, not checked here (it isn't installed).
5. **Voice hasn't been heard on a device by a person.** TsukumoKit's tests use fake audio and engines. On this Mac (`--voice-check`), Whisper read back an Apple voice and Kokoro, and Kokoro spoke, with the old KemoSabe app's downloaded models; nobody has yet clicked a bot and talked to it with a real microphone, so the end-of-speech timing, the listening ring, and barge-in are unchecked with a real voice, and Apple's recognizer hasn't run in this app (the check never asks for speech recognition, and this build hasn't been allowed it). The download consent hasn't fetched the models from Hugging Face in this app (the store and its pins are tested with a fake transport; the old app downloaded the same pins). On iPhone only the Simulator ran it, where MLX can't, so Whisper and Kokoro on an iPhone (time and memory, the low-memory guard) are unmeasured, as they were in the old app. Barge-in is by touch (clicking a bot, the microphone, or ⌃⌥D stops a reply); talking over a reply without touching anything isn't built, since it needs echo cancellation to keep the reply out of the microphone.
6. **System One hasn't decided for a real message yet.** No real Cloudflare, Jev, or custom call has been made: the owner hasn't given a token, so the request and Cloudflare's envelope are built from Cloudflare's published docs and schemas and tested against stubbed responses only. Laya hasn't been downloaded from Hugging Face by these apps (the store and its pins are tested with a fake transport; the old app downloaded the same pins), but it ran on this Mac from the old app's compiled copy through the shipping path (`TsukumoLayaTests`, October 3: routing 18 of 20 right on Tsukumo's probes, none over the 0.9 threshold, so it abstained on all of them; context 5 of 6; 22 ms warm, 4.2 s cold). `route` and `selectContext` stay at 0.9 until a proper evaluation (about 100 routing messages with held-out wording) passes, so in practice the bot last spoken to answers until a hosted model is on. Laya on a real iPhone (time and memory) is unmeasured. Watched for later, with no rows in Settings: OpenAI's Decisions API (announced September 29, 2026, in limited preview with no public contract; it would be one more `RemoteDecider`), and Amazon Bedrock's Intelligent Prompt Routing (it picks between two LLMs of a family and makes no typed decisions with probabilities, so it can't be a System One provider).
7. **`read_reference` has little to read.** The apps store KemoSabe's answers as artifacts, but nothing else yet, and the artifact store's full-text search isn't built.
8. **Keychain prompts after switching signatures.** macOS ties each saved secret (API keys, the Apple user ID) to the signature that saved it. Moving between a development build and the Developer ID (website or Homebrew) build asks once per secret for the login keychain password; **Always Allow** adds the new signature, and later builds with the same signature match it.
9. **KemoSabe's sources haven't been tried on real data.** `--ui-testing` uses stand-in permissions that never ask the system and sources that read nothing. Not checked yet: real system prompts and real data (Contacts, Photos, Messages with Full Disk Access on macOS 27, whose `chat.db` columns weren't looked at), Location and Music on a real iPhone, the "Give Message to KemoSabe" automation end to end, a real MCP server, and Apple Maps naming photo places. Left out for now, so no row pretends: Mail's own files (Mail is offered as a connected account), Notes (no API), Health (HealthKit is a capability the owner would approve in the developer portal first), and Location and Music on a Mac. Rendering the editors in `swift test` now logs that Contacts couldn't reach its service (AppKit text fields with the Contacts framework linked); nothing is read.

10. **The KemoSabe gateway hasn't met a cloud agent.** The Tsukumo relay isn't deployed (that's the owner's step, in the relay's README; the relay itself is known issue 12), so ChatGPT developer mode and dots, Claude's custom connectors, Grok's connectors, and OpenClaw have not connected through it, and no real cloud client has; the Mac's relay client ran only against an in-process fake relay and the relay's own code under `wrangler dev` on this Mac (Last verified). Not checked yet: a deployed relay over the internet (TLS, Cloudflare's WebSocket hibernation, the per-device origin form), a real Secure Enclave key in the signed app (tests and `--ui-testing` use a software key in memory; the Keychain item is unexercised), how URLSessionWebSocketTask reports a refused upgrade's status and the relay's close codes from a deployed relay (`wrangler dev` showed the registration and reconnect), sleep and wake, and a large streamed answer (over 256 KiB) through the real relay (tested against the fake). Deleting the address while the Mac is offline forgets it here only; the relay drops it after its 30-day lease. The relay's security re-review was still going on October 6, so small protocol changes may follow, in `RelayEnvelope.swift` alone. Their handshakes are tested in their published shapes against the in-app server with no network (registration, PKCE, tokens, `tools/call`), and Claude Code connected for real on this Mac. The redirect URIs and token methods in the tests follow each client's documentation and may differ in practice (Grok's callback path is a guess). Through the relay, the Mac must be awake with Tsukumo open, or callers get the relay's 503. Not checked on real data: Calendar busy times (EventKit's availability and declined events), Contacts' given and family names, a real Messages excerpt, a real photo's re-encoding, and Apple's on-device model answering a gateway question. Cards show the gateway's own words and the owner's data to be shared, never the caller's question or the name it asked about, so the owner decides an `ask` card without seeing the question (only Activity's journal records it afterward). Files and folders picked before October 6 have no anchor yet, so the gateway asks the owner to pick them again before sharing from them (KemoSabe's own reading is unchanged). A picked file's own identity isn't pinned (editors replace files when they save), only its parent folder's. Coding bots in the dock keep `ask_kemosabe` in process and don't get the typed tools; ACP agents get no gateway tools; Client ID Metadata Documents aren't supported (they'd need the Mac to fetch a client's URL), and responses are JSON, never an event stream (no call holds a connection open: anything waiting on the owner returns "escalate" at once).
11. **Meta's community pairing can't verify the phone, and the Muse gadget hasn't been paired with a real Muse app.** The SDK says so itself: community devices have no manufacturer verification, and pairing can't prevent an active man-in-the-middle. Tsukumo adds the owner's Allow on the Mac (with a code from the transcript and the phone's Bluetooth identifier on this Mac), bound to that one session, but the Muse app shows no matching code, so that Allow is the owner's judgment, not proof. Settings and the prompt say: pair at home, away from strangers, and deny any prompt you didn't start. Verified only against the SDK's published pairing vectors (every vector's transcript, keys, P-256, and client-finished record match) and in-process fakes: the Noise link against a Swift fake VM doing a real handshake, the reconnect loop and token rotation against a fake API, BLE setup and the owner's confirmation through a recording transport and a fake radio, and Muse's commands through the real Gate with the demo's data. Not checked yet: the Muse app finding and pairing with a Mac (CoreBluetooth's advertising and MTU on a real phone; macOS can't advertise the SDK's manufacturer-data "paired" flag, can't set the Mac's Bluetooth name to `MuseGadgetXXXXXX` beyond the advertised name, and can't drop a phone's connection, so a failed handshake clears the session instead); whether the Muse app waits the up to 60 seconds the owner may take to allow the phone before it sends `pairing_confirmed` (if it gives up sooner, the window needs a faster answer); whether the Muse app hands over only `api.muse.ai` and `hatch.metaaivm.com` in provisioning, the only hosts the SDK uses (anything else is refused, so pairing would fail with `auth_failed`; the log says why); a real `fetch_vms`, refresh, or `/v1/noise` session (api.muse.ai and hatch.metaaivm.com were never contacted); whether Muse accepts `platform: "macos"` (if it refuses, Tsukumo switches once to the SDK's Linux values and keeps them); how Muse's model uses Tsukumo's commands; and the Bluetooth permission prompt. The verification code isn't shown by the Muse app, so it names the attempt but can't prove which phone it is; the window says so. A `kemosabe.*` command never waits on the owner: anything the owner must decide returns `escalate` at once (the gateway's card stays in KemoSabe's chat), so Muse must call again after the owner answers, and how Muse's model handles that is untested. `bot.ask` gives the bot only Muse's words, so a bot can't use what it knows from its chat with the owner for Muse.
12. **The Tsukumo relay isn't deployed and nothing real has gone through it.** It's tested in Miniflare and by hand with `wrangler dev` and the fake Mac; no Cloudflare account has been used, so production behavior is unchecked: Cloudflare's rate limiting is per location and approximate, Durable Object alarms and hibernation on the real edge, how many device objects share an isolate (the memory budget assumes several), and whether a public client hanging up cancels a request that hasn't been answered yet (it does locally). No browser has loaded a page through it, so the sandbox's effect on the gateway's sign-in wait page (its meta refresh needs `allow-scripts`, per HTML's rules) is from the spec, not seen. No cloud agent (Claude, ChatGPT, Grok, OpenClaw) has connected through it, and the Mac's client (the public address, known issue 10) has gone through it only under `wrangler dev`. Per-device origins need a wildcard domain whose zone is on Cloudflare (relay/README.md). Whether each cloud client accepts an issuer with a path is from the specs, not seen. The registry's device count is eventually consistent: a race or lost message can leave it high for about one period plus one reconciliation pass (it's an anti-abuse limit, not a security boundary). Per-device rate counts and the nonce key reset when the device's object hibernates (a challenge issued just before then is refused; the Mac asks again). Someone with many addresses could fill the device cap over days; the fallback is an enrollment token (not built). By design the relay sees requests and answers in transit after TLS (tokens, OAuth codes, what the owner allowed out), and an actively malicious operator could alter them; it stores none of it and logs no content ([docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#the-tsukumo-relay)). The test pool's bundled wrangler (4.124) warns about `redact_query_string`; the pinned wrangler 4.147 that deploys knows it. In the tests workerd prints "uncaught exception … relay ended the response" when the relay ends a stream; that's the runtime reporting the aborted body, and the tests check the client sees the error.
13. **Software Update hasn't installed a real release yet.** Every step is tested with disk images made on this Mac and fake, ad-hoc-signed apps, and the signature and notarization checks passed on a real notarized Developer ID app by the same team (MacSpaces); the swap, the relaunch helper, and the feed have not run against a real notarized Tsukumo DMG from zlichtman.com, since no release has carried the updater. The first one to try it is 2.04 updating to a later build. Until a build with the updater is installed, owners of 2.00 to 2.03 update by downloading the DMG (those builds have no updater), and `tsukumo.json` wasn't on the site on October 6 (404), so the feed must be published with the next release (Release, step 3). The builds on the site were named `Tsukumo-Dock-2.0N.dmg` by hand while the script names them `Tsukumo-2.0N.dmg`; the app accepts any `.dmg` under `/downloads/` on zlichtman.com, but the feed's `url` must be the real file. A notification for a ready update appears only if the owner has allowed Tsukumo's notifications (asked when they turn on Download updates automatically). If Tsukumo is installed somewhere the owner can't write (an admin-owned /Applications copy), it offers the download instead of asking for a password, and so does a volume that can't swap atomically (no two-step fallback). The new copy replaces the running one where it is, under its own name, so a copy kept outside /Applications is updated in place. A process running as the owner could still change things between checks; that's outside the threat model (docs/ARCHITECTURE.md, TsukumoUpdate), and every check runs again before and after the swap and before the relaunch.

14. **Your bots wait on the owner's look.** (a) Only Claude's spark and OpenAI's blossom ship as official marks; Grok, Muse, OpenClaw, Cursor Agent, and Gemini CLI show initials until the owner adds each company's mark from its press kit as `TsukumoKit/Sources/TsukumoUI/Resources/ServiceMark-<id>.png` (and its line in `ART-NOTICE.txt`). (b) KemoSabe's Two-tone look, an option beside its cloud, is close to Finder's face; the owner accepted the trademark and App Review risk. (c) Codex pets and the owner's dot are read from Codex's own files (the ChatGPT app's `app.asar`, `~/.codex/pets`, and `~/.codex/.codex-global-state.json`, of which only the dot's name, pet, and IDs are read): none is a published interface, so a Codex update can change them, and then the pets don't show (bots wear their marks) and Add a Bot doesn't offer the dot. Nothing of OpenAI's ships in Tsukumo. A dot can't be messaged from another app; its tile opens it in Codex. A cloud pet (an ID starting `pet_`) isn't drawn. A gateway caller's name can't be checked, so it counts for a service only once the owner confirms which one it is; sync's aliases and schema are tested in memory only, since no build has iCloud on. Not seen yet: a real dot and real pets on the live dock (the tests use made-up archives and pet folders, and one optional test reads the real ChatGPT app's Seedy), Tinted glass on the live dock by the agent that built it (look with `--ui-testing --dock-style tinted`), and a Muse app finding this Mac. Up to 2.08 it couldn't: macOS gives a peripheral 28 bytes of advertisement, and the 128-bit service UUID left room for only "MuseGadg" of the name, so the Muse app (which finds gadgets by name) never listed the Mac; from 2.09 the Mac advertises the name only (`MusePeripheral`). The macOS limits that remain: no manufacturer data (the SDK's paired flag) and the Mac's own GAP name.
15. **The Claude bot hasn't run a real task in the app.** Its tests use a fake Claude Code and a fake API engine with the real gateway and Gate on made-up items; one real read-only task ran through the module on sealed Claude Code (Last verified), not in the app, and not on an API key. Not checked yet: a real `ask_kemosabe` from Claude (through the SDK MCP server) waiting on a gateway card for minutes (Claude Code's own tool timeout may end the call first), an approval from a real Ask first run, Auto-edit writing files that reach the Inbox, `--resume` of a session that was killed mid-turn, a schedule across days, a real time zone change notification, and the chat tab with a real engine. There's no OS sandbox around Claude Code: the boundary trusts Claude Code's own enforcement of its flags and deny rules (docs/ARCHITECTURE.md, the Claude bot's trust boundary). The gateway answers one question per caller at a time, so two Claude tasks asking at once get "busy" for the second. Secret files are recognized by name only. Settings, Gateway lists Claude with the paired device's icon. The engine and model choices live in the panel's menu, not in Settings, Models. Sealed runs have no commands and no web search (owner decision whether to offer either, behind Ask first).
16. **The other coding bots aren't sealed yet** (the security review's findings 1 and 2 are harness-wide). Claude Code bots, Codex, Cursor Agent, and Gemini CLI still start with the owner's whole environment and their own setup, and a read outside the bot's folder becomes a card. Each needs its sign-in kept working, verified with `CodingSmokeTests`.
